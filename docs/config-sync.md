# AI configuration sync runtime and contract

Installation and login orchestration remain shell and PowerShell. The four
`*-sync` entrypoints delegate configuration/file operations to the
small `lib/config_sync.py` backend. It uses Python's standard-library JSON
implementation and `tomlkit` for syntax-aware TOML edits; no AWK/regular-expression
TOML parser or alternate jq merge implementation remains.

In this checkout the backend is
`common/codex/coding-agent-kit/lib/config_sync.py`, in the coding-agent-kit
submodule. The four launchers, `lib/sync-runtime.sh`, `setup-sync.sh`,
`setup-sync.ps1` and `requirements-sync.txt` stay here as regular files, so the
`.venv-sync` provisioned below keeps working; the submodule carries reference
copies for its own tests, identical except that `lib/sync-runtime.sh` and
`setup-sync.*` here name the engine inside the submodule. See
[coding-agent-kit](coding-agent-kit.md)
for delivery, updates and the uninitialized-submodule behavior.

## Explicit provisioning

All AI helpers require Python 3.11 or newer. Codex TOML sync additionally needs
the exact pure-Python `tomlkit` version in `requirements-sync.txt`; setup verifies
its wheel hash. Claude JSON, Codex rules and Codex instructions use only
Python's standard library.
To provision the complete installer runtime on each checkout/device, run one of:

```sh
./setup-sync.sh
# Or select a particular installed interpreter, including a path with spaces:
./setup-sync.sh --python /path/to/python3
```

```powershell
./setup-sync.ps1
# Or:
./setup-sync.ps1 -Python 'C:\path with spaces\python.exe'
```

Setup creates the ignored, checkout-local `.venv-sync/`, installs only the
pinned wheel, and validates the runtime. It does not require activation, root,
global pip installs, conda activation, or a new shell-startup PATH entry. It
refuses an unrelated directory or a linked virtual environment. It does not
install Python itself; select an already installed supported interpreter.

Profiles, installers, and automatic updates **never** install or download
AI-sync/parser dependencies. A missing runtime, or a changed required parser version after a
pull, fails with a request to rerun explicit setup. An offline host can provision
from a previously downloaded matching wheel using pip's normal offline options
(for example `PIP_NO_INDEX=1` and `PIP_FIND_LINKS=/path/to/wheels`).

The clone must remain present for its stowed wrappers to work, just as for other
Stow-managed files. Re-provision rather than copying virtual environments to a
different OS, Python installation, or checkout location.

## Helper contract

The helper interface, the runtime lookup (`DOTFILES_SYNC_PYTHON` or
`.venv-sync`), merge ownership, `--hooks`, the Codex instructions overlay,
the migration semantics, file safety and the engine tests are documented with
the engine in
[coding-agent-kit's `docs/config-sync.md`](https://github.com/FridrichMethod/coding-agent-kit/blob/main/docs/config-sync.md)
(in this checkout: `common/codex/coding-agent-kit/docs/config-sync.md`).
`tests/ai-integration.sh` reruns those engine tests on this checkout's real
`config.toml`, `settings.json` and `portable.rules`.

## Codex instructions wiring

`stow-all.sh` passes `--append "$HOST_DIR/sherlock-kit/.claude/rules/sherlock-kit.md"`
when that link exists on the selected host and runs the helper without it
everywhere else, so moving to a host without rules removes a stale override.
When the link exists but does not resolve, because the submodule is not
initialized yet, it warns `sherlock-kit submodule not initialized; Codex
instructions left unchanged (git submodule update --init --recursive)`, skips
this helper's preflight and apply only, and completes the rest of the stow.
That run remembers the host but records no applied HEAD, since an
uninitialized submodule looks clean to `git status`. The next login updater
therefore initializes the submodule and restows; to finish at once, initialize
it and rerun `./stow-all.sh HOST`. The override is otherwise regenerated by the
next `./stow-all.sh HOST`, which the login updater runs after it pulls a
submodule bump; after editing the portable `AGENTS.md` or bumping the
submodule by hand, rerun it yourself. The step is POSIX only: no Windows host
carries the rules, so `stow-all.ps1` has no counterpart.

## Legacy portable cleanup

To clean known legacy runtime state out of this checkout's tracked Codex
baseline, read the migration safeguards in the engine's `docs/config-sync.md`
first, then run the explicit migration from the checkout root:

```sh
common/codex/.local/bin/codex-config-sync --migrate-portable \
    common/codex/.codex/config.toml /path/to/live/config.toml
```

It rewrites `common/codex/.codex/config.toml`; review the tracked diff.
